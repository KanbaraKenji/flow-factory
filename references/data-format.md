# flow.json 数据格式（schema `flow-factory/0`）

一张图 = 一份 `flow.json`。AI 读完代码填这份数据，`scripts/build.py` 校验后塞进渲染器，出一个自包含的 HTML 页面。**不写坐标**，布局全部自动算。

## 顶层

```jsonc
{
  "schema": "flow-factory/0",
  "page": "dev",                 // dev = 研发流程图（只读代码就能画，默认）；monitor = 运行监控图（要有 runs，见「运行记录」）
  "title": "网店订单处理",        // 页面标题，2~12 字
  "subtitle": "从下单到签收 · 样例货为虚构",
  "summary": {                   // 一眼看懂「从什么到什么」：帮你定范围用，页面不显示（2026-10-26 页头减法）
    "input": "顾客在网页上提交的订单",
    "output": "包裹送到顾客手里，订单标记完成"
  },
  "source": {                    // 依据哪一版代码画的：给 AI 判断要不要重画，界面上不显眼
    "repo": "D:/dev/shop",
    "rev": "git:3f2a9c1",        // 有 git 写 git:<短哈希>；没有就写 mtime:<最新文件修改时间>
    "files": ["server/order.py", "server/pay.py"],
    "drawn": "2026-10-24"
  },
  "lines": [ ... ],              // 流水线（一条主流程一条线），至少 1 条
  "stations": { ... },           // 站点（流程里的每一步）
  "products": [ ... ],           // 成品库（主流程走完货落到哪里），至少 1 个
  "stores": [ ... ],             // 被写入的地方（数据库、文件、外部服务……），可为空
  "samples": [ ... ],            // 可选。样例货：几件典型的输入；不写则自动播放演遍全部路线
  "layout": { "cols": 6 },       // 可省：强制每行几站（3~10）。不写就按画布宽高比自动挑
  "runs": { ... }                // 可省：运行记录，见文末
}
```

## lines：流水线

```jsonc
{ "id": "main", "name": "订单主线", "color": "#3b82c4",   // color 可省，按调色板自动给
  "stations": ["receive", "pay", "stock", "pack", "ship"], // 按正常顺序排的站
  "product": "done",                                       // 最后一站正常走完进哪个成品库
  "then": "refund",          // 可省，与 product 二选一：最后一站正常走完接到哪（线 id = 接那条线的第一站；站 id = 汇入那一站，比如第二个入口汇入主线中段）。画成实带
  "trigger": "每分钟一轮",    // 可省：这条线怎么被触发（定时、事件、人点按钮），显示在线名旁
  "per": "每镜一份",         // 可省：这条线是对每一份分头跑的，显示在线名旁（真要画拆与合，用站上的 split / join）
  "via": "auth",            // 可省：这条线的货都先过这个公共站（见下面「四种结构」）
  "every": "1 分钟" }        // 可省：这条线定时反复跑，线头卡上挂「⟳ 每 1 分钟」（≤ 8 字）
```

- 每个站最多属于一条线。不属于任何线的站（比如几条线共用的人工台、只有出错才走到的补救站）叫「旁站」，自动放在送货来的那一站所在行的下方。
- 一条线长了会自动折成蛇形；每行几站按画布宽高比在 3~10 里挑（宽屏偏宽、手机偏长），不用管。
- 几段工序前后相接（剧本 → 首帧 → 出片 → 成片）就写成几条线，前一条用 `then` 接后一条，只有最后一条写 `product`。

## stations：站点

```jsonc
"pay": {
  "name": "收款",                // 站名，≤ 8 个汉字（长了会被校验拦下）
  "kind": "step",               // in 入料 · step 加工 · check 检查 · gate 闸门（会拦货）· hand 人工 · ai AI 模型执行 · out 出货
  "actor": "浏览器",             // 可省：谁在执行（浏览器 / 后端 / 看门狗进程 / 值守会话……），显示在站卡上；多进程交接时一定写
  "does": "向支付平台扣款，等到账回调",   // 一句话：这一站干什么（≤24 字）
  "detail": "回调超时 15 分钟算挂起；同一订单号只扣一次",   // 可省：副作用、设计理由、容易忽略的静默行为。不计字数，只在面板折叠区显示
  "input": "待付款订单",          // 进来时货长什么样
  "output": "已付款订单",         // 正常出去时货长什么样（形态变化是看懂「输入到成品」的关键，尽量写）
  "code": "server/pay.py:88 charge()",   // 代码位置：给 AI 用，界面只在折叠区显示，可省
  "writes": [ { "store": "db", "what": "orders.status = 已付款" } ],
  "reads":  [ { "store": "db", "what": "按订单号查是否扣过" } ],   // 可省：读了哪里。A 站写、B 站读，就能看出两站经由它交接
  "irreversible": {             // 做了就收不回的动作：delete 删除 · overwrite 覆盖 · send 对外发送（扣款、发消息、推送、上传都算）。一站有几个就写成数组
                                // 覆盖旧值但无害的写入（比如重写一个缓存）不必标
    "type": "send",
    "what": "向支付平台扣顾客的钱",
    "protection": { "level": "ok", "note": "扣款前查重复订单号，同一单不会扣两次" }
  },
  "default": "ok",              // 正常情况走哪个岔路
  "branches": [ ... ],          // 至少 1 条
  "unhandled": null             // 这一站看不到任何出错出口时，写清「出错会怎样」（见下），否则省略
}
```

### inner：站内小流程（可选）

这一站自己要走好几步才得出结果时，把那几步写成站内小流程。什么时候该用，见 SKILL.md 第 3 节「站内小流程」。

```jsonc
"pay": { "name": "收款", ..., "branches": [ { "k": "ok", ... }, { "k": "timeout", ... }, { "k": "cancel", ... } ],
  "inner": {
    "lines": [ { "id": "pay_in", "name": "收款站内", "stations": ["charge", "wait_cb", "book"] } ],  // 不写 product / then
    "stations": {
      "charge":  { ..., "branches": [ { "k": "ok", "when": "平台受理了请求", "to": "next" } ] },
      "wait_cb": { ..., "branches": [
        { "k": "paid",    "when": "回调说已到账",   "to": "next" },
        { "k": "timeout", "when": "15 分钟没回调",  "to": "exit", "exit": "timeout", "fault": { ... } },  // 出站，走外面的 timeout
        { "k": "cancel",  "when": "到账前顾客取消", "to": "exit", "exit": "cancel",  "fault": { ... } } ] },
      "book":    { ..., "branches": [ { "k": "ok", "when": "订单改成已付款", "to": "exit", "exit": "ok" } ] }
    },
    "layout": { "cols": 3 },     // 可选
    "samples": [ ... ]           // 可选；一般不写，页面会用外面样例货的 in 和站内全部路线
  } }
```

- 站内的站与外面的站同一套字段（可以再嵌一层 `inner`），站 id 不能和外面重名；写入目标用外面的 `stores`。
- **契约**（校验器报错）：站内每个出口 `to: "exit"` 的 `exit` 必须是外面这一站某条岔路的 `k`（几条岔路走外面同一条带子时，页面上共用墙上的一个开口）；外面每条岔路至少有一个站内出口能走到；站内不能 `to: "end"` 停住，站内的线最后一站走 `next` 也会报错（没有去处）。
- 外面这一站的 `branches` 照常写（它们就是站内的结论），`writes` / `irreversible` 可以在外面写个总的，也可以只写在站内具体那一步。

## branches：岔路

每条岔路回答「什么情况下货往哪走」。

```jsonc
{ "k": "ok", "when": "支付平台回调到账", "to": "next" }
{ "k": "timeout", "when": "15 分钟没收到回调", "to": "end",
  "end": { "kind": "wait", "label": "订单挂起，下一轮再查" },
  "fault": { "kind": "retry",
             "user_sees": "订单显示「付款确认中」，最多等 15 分钟",
             "verdict": { "level": "ok", "note": "设计好的兜底：每轮重查一次，到账就继续，不用管" } } }
{ "k": "refund", "when": "顾客在确认前取消", "to": "refund_desk",
  "fault": { "kind": "human", "user_sees": "客服后台多一条待退款", "verdict": { "level": "risk", "note": "退款台没有超时提醒。建议：停留超过一天推一条提醒" } } }
```

- `when`：**人话**，写触发条件本身，不写变量名、函数名。好：「同一部作品已经有单在下载」。坏：「_wash_overlap() 返回 409」。
- `to`：`"next"` = 本线下一站（最后一站的 next = 本线的成品库）；`"<站 id>"` = 跳到别的站；`"back"` = 回到把货送来的那一站（人工台处理完退回原闸）；`"end"` = 货停在这里，必须带 `end`。
- `end.kind`：`done` 成功收尾（不进成品库的另一种成功）· `wait` 停住等下一轮 · `blocked` 停住等人 · `returned` 退回给发起人 · `failed` 这一单失败 · `stuck` 卡死（停住且不报错、没人知道）。
- `fault`：这条岔路是「出错时的去向」才写。`kind` = `retry` 下一轮自动再试 · `human` 转人工 · `degrade` 带病放行（货照样往下走，但成品有缺陷：数据记错了人、校验有错照样放行、占位字送进下游……）· `stop` 中止 · `stuck` 卡死。走过 `degrade` 岔路的样例货进成品库时标「带病」。
- 岔路也可以带 `writes`：只在走这条岔路时才写的东西（默认：正常岔路沿用站点的 writes，出错岔路不写）。
  - `user_sees`：对用户的后果——他在界面上、手机上、成品里会看到什么。
  - `verdict.level`：**要不要用户关注**。`ok` 设计好的兜底、不用管 · `risk` 有隐患（再试也好不了、停住没人提醒、失败不留痕……）· `bad` 没处理、卡死、代码缺陷，或收不回的步骤缺保护。
  - `verdict.note`：AI 的判断（≤48 字），`risk` / `bad` 必须带「建议：……」；`ok` 写一句为什么不用管（「当场退回让人改」「宁可停也不乱写」）。
  - `verdict.why`：可省，判断的依据——推导过程、有几分把握（「代码推断，未看日志」）、出处（某条判例、某行代码）、规模（「20 个对话 36 小时无 RC」）。不计字数，点开那条岔路才显示。`protection` 和 `unhandled.verdict` 同样可带 `why`。
- 正常岔路（不是出错）不写 `fault`。

## unhandled：这一站出错会怎样没写

一站所有岔路都没有 `fault` 时，渲染器会在故障视图把它标成「未处理」。读代码后如果确认「这站几乎不会出错」或「出错有外层兜底」，也要写清楚：

```jsonc
"unhandled": { "user_sees": "如果打包服务挂了，订单停在已付款", "verdict": { "level": "risk", "note": "出错去向没写。建议：补一个失败出口并记日志" } }
```

## products：成品库

```jsonc
{ "id": "done", "name": "已签收", "desc": "顾客收到包裹，订单完成" }   // desc ≤ 30 字
```

## stores：写入目标

```jsonc
{ "id": "db", "name": "订单数据库", "kind": "db" }   // name ≤ 10 字；kind：db 数据库 · kv 键值 · file 文件 · queue 队列 · api 外部服务 · log 日志 · notify 通知
```

## samples：样例货

样例货是**几件典型输入**（正常的一件 + 最要紧的出事几件），画布上按拍子沿路线走，用户点它跟踪，看它一路变成什么样。

**可选**。页面总会自己算「全部路线」：从每个入口（不被别的线 `then` 接过来的线的第一站）深度优先走遍每条岔路，每站先走 `default`；同一站一条路线里最多进两次、同一条岔路不走两次（防绕圈）；`back` 回到上一步那站；`end` / 进成品库 / 没有下一站时收尾；最多 60 条。`build.py` 用同一套规则报出条数和最长步数，写不写、写几件由出图的人按 SKILL.md 第 2 节第 4 步判断。演练里「复制成样例货」生成的 JSON 与本节格式相同，`path` 可直接粘进来。

```jsonc
{ "id": "s1", "name": "普通订单", "badge": "普",          // badge：一个字，显示在货箱上
  "desc": "一件现货，顾客正常付款",
  "input": "订单 #1001：蓝色帆布包 ×1",                     // 原料
  "path": [                                               // 一步一站，按顺序；每步写走了哪条岔路
    { "st": "receive", "br": "ok" },
    { "st": "pay",     "br": "ok",   "form": "已付款订单 #1001" },   // form：经过这一站后货的样子，省略 = 沿用上一步
    { "st": "stock",   "br": "ok" },
    { "st": "pack",    "br": "ok",   "form": "包裹 SF1234" },
    { "st": "ship",    "br": "ok",   "form": "顾客签收的包裹" }
  ] }
```

某一步写了 `in`，自动播放演到这一站时会进站内把这段演一遍再出来（不写就不进，这是默认）：

```jsonc
{ "st": "pay", "br": "cancel", "in": [ { "st": "charge", "br": "ok", "form": "扣款请求 P-2071" }, { "st": "wait_cb", "br": "cancel" } ] }
// in 的最后一步必须是站内出口，且出口等于这一步的 br
```

- 路线必须沿真实的岔路走（校验器会核对每一步的 `br` 是否通向下一步的 `st`）。
- 最后一步走 `next` 出线 → 进成品库；走 `end` → 停在那一站，显示结局。
- 样例货是虚构的，副标题里写明「样例货为虚构」。

## 四种结构（可选，有就写）

**① 拆成很多份分头跑、再拼回一件**

```jsonc
"cut":   { "name": "拆镜", ..., "split": { "by": "镜", "n": 6 } },   // 到这里拆成很多份；n 可省（页面显示 ×N）
"merge": { "name": "拼接", ..., "join":  { "by": "镜" } }            // 等齐再合成一件
```
- 拆与合之间的带子画成三股带；货箱在这段变成一摞，角上标 ×N。样例货某一步可写 `"n": 5`（这时还剩几份，比如一镜出事被分出去）。

**② 每个请求都先过的公共站**

```jsonc
"lines": [ { "id": "reg", "name": "注册线", "via": "gate", "stations": [...] },
           { "id": "rec", "name": "记录线", "via": "gate", "stations": [...] } ],
"stations": { "gate": { "name": "验登录限流", ..., "branches": [ { "k": "ok", "when": "登录有效且没超频", "to": "next" }, ... ] } }
```
- 公共站不放进任何线的 `stations`；它的 `to: "next"` 按 `via` 它的线展开（演练时每条线一个选项，全部路线也逐条展开）。
- 样例货路径：先走公共站，下一步写那条线的第一站。

**③ 定时反复跑、跨轮计数**

```jsonc
"lines": [ { "id": "tick", "name": "看门狗", "every": "1 分钟", "stations": ["wake", "steward"], "product": "back" } ],
"steward": { ..., "branches": [
  { "k": "retry",  "when": "没接上，还没试满 3 次", "to": "again", "count": { "name": "值守尝试", "max": 3 }, "fault": { ... } },
  { "k": "giveup", "when": "试满 3 次还没接上",     "to": "end", ... } ] }
```
- `to: "again"`：下一轮从这条链的线头再来（沿 `then` 往前找第一条线；那条线有 `via` 就回公共站）。线头不对时写 `"head": "<站 id>"` 指定回到哪一站（比如计数发生在旁边那条线上）。线头那条线最好写 `every` 或 `trigger`，不然看图的人不知道「下一轮」是什么时候。
- 样例货可以真的绕回线头再走：`[wake.ok, steward.retry, wake.ok, steward.retry, wake.ok, steward.ok]`。页面自动数第几轮、`count` 到几了（只数路径里走过的 `again`），写在货箱头顶。

**④ 同一步有两种入口**

```jsonc
"frame": { "name": "出首帧", ...,
  "modes": [ { "id": "script", "name": "脚本", "how": "h3_shot.py 批量", "diff": { "GPU 锁": "先写锁", "一次": "整版每镜" } },
             { "id": "ui",     "name": "界面", "how": "ComfyUI 手点",   "diff": { "GPU 锁": "不写锁", "一次": "单张" } } ],
  "branches": [ { "k": "ok", ... }, { "k": "oom", "when": "显存被聊天模型占了", "only": "ui", ... } ] }
```
- 入口名 ≤ 4 字（卡上并排放）；`diff` 的键是对照的项目，面板里两栏对照。`only`：只在这种入口才会走的岔路。样例货某一步可写 `"mode": "ui"`，货停在这站时卡上的切换跟着亮。

## 运行记录（可选；有真实统计才写）

```jsonc
"page": "monitor",          // 可省；写 monitor = 运行监控图：打开就在「运行」视图，副标题前写「运行监控图」
"runs": { "from": "10-24 00:00", "to": "10-25 23:59", "total": 137, "note": "rc_autostart.log 统计" },   // 顶层：统计的时间段、总件数、来源
"stations": { "steward": { ..., "runs": { "n": 31, "stuck": 0, "last": "10-25 23:51" },               // 进站几件、现在卡着几件、最近一次
  "branches": [ { "k": "retry", ..., "runs": { "n": 6, "last": "10-25 22:10" } } ] } }                  // 这条岔路走过几次
```
- 有 `runs` 就多一个「运行」视图：带子按走过的次数加粗、标次数；`n: 0` 的岔路画黄虚线（没走过）；站卡写「进 N」「卡 K」。
- 次数要从日志、数据库、任务历史里统计出来，写清来源（`runs.note`）；统计不出来就别写，不要估。

## 版本对比（可选；构建时生成，不写进 flow.json）

`build.py flow.json -o flow.html --prev 上一版.flow.json`：按站 id 比两版，算出新加 / 删掉 / 挪动（换线或前后站变了）/ 改动（站名、一句话、种类、执行者、岔路增删、条件、去向、判断等级、站内流程）的站，页面里多出「对比上一版」。
